# SQL ModernRock: оптимизация 23.09.2026

## Измеренный результат

Проверены активная тема ModernRock_new и собственные обработчики городской афиши/концертных страниц. Замеры — исполнение WordPress через PHP 7.4 с `SAVEQUERIES`, а не скорость сети браузера. WordPress 6.6.7, MariaDB 10.7.8; постоянный object cache при проверке не подключён.

Ниже один исходный профиль и диапазон двух финальных профилей. SQL-кэш MariaDB, нагрузка сервера и состояние API-кэша влияют на время; это контрольные замеры, не гарантированные задержки для каждого посетителя.

Эти отдельные SQL-запросы дополнительно проверялись с `SQL_NO_CACHE`.

## Что было неудачно и что изменено

### Запросы на каждую концертную карточку

У «16 Тонн» на 50 карточек приходились 50 отдельных поисков картинки и ещё 50 поисков ссылки артиста. Затем отдельно читались публикации, метаданные изображений и transient каждого предложения.

Новый модуль `sql-performance.php` загружает совпадения артистов пачками, затем пакетно заполняет кэш публикаций, миниатюр и параметров transient. Повторяющиеся и отсутствующие имена учитываются в рамках запроса. Поиск по точному названию сохраняет правила сравнения SQL; запасной поиск по slug выполняется отдельно, без OR между разными индексами.

В проверке 53 имён результаты старого и нового поиска ID/slug совпали. Пакетная подготовка потребовала 7 запросов; последующий цикл получения ссылок и картинок — 0 дополнительных запросов. Разметка карточек сохранена.

Обычные списки публикаций также заранее подгружают миниатюры, поскольку старые шаблоны вызывают `wp_get_attachment_image_src()` напрямую и обходят автоматическую пакетную загрузку WordPress.

### Списки артистов и площадок в админке

В 11 селектах использовались WP_Query до 10 000 полных публикаций, с телом, метаданными и рубриками. Один список артистов дополнительно занимал около 148 МиБ памяти.

Теперь WordPress определяет подходящие ID с прежними правилами статусов, прав, рубрик и сортировки, а затем загружаются только ID и заголовки. Форматирование названий сохранено через фильтр `the_title`; список повторно используется внутри запроса. Между пользователями данные селектов не кэшируются.

Проверены совпадение и порядок 10 000 названий артистов и 757 площадок, включая черновики и названия с HTML-сущностями. Изолированная новая загрузка артистов заняла около 6 МиБ дополнительной памяти и 0,07–0,15 с против примерно 0,93–1,11 с старой. Повторные обращения в этом запросе не делают SQL.

Лимит 10 000 сохранён. Отдельная переделка самих селектов в поиск по мере ввода не выполнялась.

### Главная, новости и боковые блоки

Основная выборка главной и новостей задаётся до выполнения SQL и используется шаблоном повторно: 21 публикация на главной и 15 в новостях, с прежними фильтрами и пагинацией. Убраны дублирующие запросы шаблонов.

В рекомендациях, других новостях, связанных материалах артиста и быстрых подсказках отключены ненужные `SQL_CALC_FOUND_ROWS`/`FOUND_ROWS()`. В полной пагинируемой выдаче подсчёт сохранён.

По просьбе владельца сохранено прежнее поведение «Концертов сегодня»: если ID событий на текущую дату отсутствуют, пустой `post__in` оставляет общую подборку концертной рубрики. Оптимизация SQL и отключение ненужного подсчёта строк сохранены. Строка главной в таблице обновлена по двум замерам после восстановления этого поведения: первый запуск — 158,2 мс SQL, повторный — 17,5 мс.

Прошедшие концерты артиста сохранены: вместо SELECT * читаются только ID и даты, имя передаётся через prepare. Поиск ID площадки также ограничен одной строкой, параметризован и повторно используется внутри запроса.

### Жанры и сброс кэша

Большая карта жанров больше не распаковывается заново для каждой карточки. В SQL истории убран DISTINCT по длинным текстовым полям: итоговый код уже удаляет повторяющиеся жанры. Равенство результатов проверено отдельно до подключения.

Добавление индекса для соединения post_id/meta_key и упрощение запроса снизили измеренное время полного перестроения карты приблизительно с 1,75 с до 0,75 с. Итоговая карта из 4 776 имён совпала с прежней. Пятьдесят повторных обращений в одном запросе не выполняют SQL и не распаковывают transient заново.

Кэш сбрасывается при изменении/удалении артиста или старого концерта, изменении жанровых полей и соответствующих рубрик. Учитываются и прежние рубрики при удалении связи. Сохранение обычной новости больше не заставляет следующего посетителя перестраивать все жанры.

В штатной SQL-очистке API-кэша экранированы подчёркивания префиксов LIKE. Теперь это буквальные префиксы для индекса option_name, а не ведущие SQL-маски. Массовая очистка кэша в рамках этой работы не запускалась.

### Поиск

Полный поиск по текстам на примере Oasis выполнял запрос около 700 мс. Добавлен кэш ID, количества результатов и числа страниц на 90 секунд для публичных форм поиска сайта, артистов/площадок и подсказок.

Кэш использует штатный `posts_pre_query`; условия сопоставления, ранжирование, порядок, рендеринг публикаций и пагинация сохранены. При сохранении публикации/страницы, удалении записи или смене рубрик меняется поколение кэша. Для вошедших пользователей и админки используется обычный запрос.

В отдельной проверке совпали ID, порядок и счётчики для Oasis, второй страницы, запроса с кавычкой и & и отсутствующих результатов. Проверен сброс. В финальном повторном профиле `/search?q=Oasis` суммарное SQL-время страницы составило 8,4 мс; это попадание в кэш, не ускорение первого нового текстового поиска.

Первый уникальный запрос по текстам по-прежнему использует стандартный LIKE WordPress. Нативный путь `/?s=...` сохраняет свой стандартный основной запрос. Они проверены на работоспособность, но не заменены поиском с другой семантикой.

## Изменения базы: применены отдельно от Git

Добавлены три неуникальных индекса в существующие таблицы. Данные публикаций и метаполей не удалялись. Перед выполнением использовался `SET SESSION lock_wait_timeout=5`; создание выполнялось с `ALGORITHM=NOCOPY, LOCK=NONE`.

```sql
ALTER TABLE wp_posts
  ADD INDEX mrock_title_lookup (post_title(160), post_status, post_type),
  ALGORITHM=NOCOPY, LOCK=NONE;

ALTER TABLE wp_postmeta
  ADD INDEX mrock_meta_lookup (meta_key(64), meta_value(160), post_id),
  ALGORITHM=NOCOPY, LOCK=NONE;

ALTER TABLE wp_postmeta
  ADD INDEX mrock_post_meta (post_id, meta_key(64)),
  ALGORITHM=NOCOPY, LOCK=NONE;
```

Это журнал уже выполненных команд с текущим префиксом wp_, не автоматическая миграция темы. При переносе нужно сначала проверить существующие индексы. Создание заняло около 5,2 / 16,5 / 9,1 с соответственно. Штатные индексы WordPress сохранены.

EXPLAIN подтвердил переход поиска названия с полного сканирования wp_posts к mrock_title_lookup; поиск group_afisha/meta_value использует mrock_meta_lookup. mrock_post_meta ускоряет соединение записи с конкретным метаполем.

Выбор режима создания соответствует [документации MariaDB NOCOPY](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-online-ddl/innodb-online-ddl-operations-with-the-nocopy-alter-algorithm). Краткие metadata-lock на этапах DDL возможны; ожидание ограничивалось указанным тайм-аутом.

Для возврата схемы достаточно удалить только эти три именованных индекса. Откат PHP через Git сам индексы не удаляет; они не меняют содержимое данных. Их наличие не требует включать новый код темы.

## Границы результата

Замеры относятся к текущим данным и конфигурации. Во время одного прогона городская афиша ждала внешний API около 8 секунд при SQL-времени около 23 мс; оптимизация базы не устраняет ожидание внешнего сервиса. На запросе с уже доступными данными она отрабатывала быстрее.

Старая календарная афиша и её шаблоны не переписывались. Ядро WordPress, сторонние плагины и все исторические запросы вне проверенных активных путей не рефакторились.
